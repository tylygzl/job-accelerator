# 简历与面试准备

这份文档只服务投递和面试表达。技术实现以 `server.py`、`pipeline.py`、`plugin/` 和其他文档为准。

## 简历项目描述

**求职加速器 | Chrome 插件 + FastAPI + LLM 的半自动求职助手**

技术栈：Python / FastAPI / Pydantic / Chrome Extension / JavaScript / LangGraph / LLM API / Nginx / systemd

项目简介：面向 BOSS 直聘求职场景，开发半自动岗位筛选工具，解决人工逐条阅读 JD、判断匹配度、重复编写开场白效率低的问题。系统由 Chrome 插件、FastAPI 后端和匹配流水线组成，支持岗位抓取、简历技能画像、匹配度计算、LLM 开场白生成、结果展示和 CSV 导出。

核心工作：

- 设计 Chrome 插件读取 BOSS 搜索页岗位卡片和右侧 JD，并调用后端 `/match` 接口返回匹配报告。
- 使用 FastAPI + Pydantic 实现后端接口，统一返回 `success/data/message/request_id`，并对 JD、简历文本和模式参数做输入校验。
- 实现两阶段匹配策略：本地规则先快速计算匹配分，高潜岗位再调用 LLM 生成定制开场白，避免每条岗位都调用模型导致成本和延迟过高。
- 支持匹配度阈值、排除关键词、岗位标题/地点过滤、HR 活跃度过滤、24h 缓存、页面会话去重、暂停/继续、每日目标和 CSV 导出。
- 增加 token 鉴权、限流、并发门控、全局异常处理、结构化日志和 Trace JSONL，便于朋友测试和线上问题复盘。
- 编写固定 JD 回归评测集，统计通过率、平均分和失败样本，当前本地规则评测 `12/12` 通过，用于迭代评分规则。
- 部署到阿里云，使用 systemd 常驻运行，Nginx 反向代理到 `/job-accelerator/`，并提供朋友体验版插件打包脚本。

项目结果：

- 打通从 BOSS 岗位扫描、后端匹配分析、LLM 开场白生成到插件展示/导出的完整闭环。
- 支持云端后端 + 本地 Chrome 插件的朋友小范围测试，接口具备鉴权、限流、并发保护和 Trace 复盘能力。

注意：不要把 `12/12` 写成真实线上准确率，只能说是固定样本回归评测结果。

## 1 分钟讲稿

这个项目是我为自己找实习做的半自动求职工具。整体架构是 Chrome 插件加 FastAPI 后端：插件负责在 BOSS 搜索页读取岗位卡片和 JD，后端负责解析简历和岗位要求，计算匹配分，并返回命中技能、缺失技能、风险提示和投递建议。

为了降低模型成本和等待时间，我没有每条岗位都调用 LLM，而是先用本地规则做快筛，只有高潜岗位才调用 LLM 生成定制开场白。插件侧还做了匹配度阈值、关键词过滤、HR 活跃度过滤、24h 缓存、暂停继续、CSV 导出和自动填入开场白。

工程化上，我给后端加了 Pydantic 校验、统一响应结构、token 鉴权、限流、并发门控、日志和 Trace 记录。项目已经部署到阿里云，用 systemd 常驻运行，Nginx 反向代理；另外有固定 JD 回归评测集，当前本地规则 12 条样本全部通过，用来防止后续改规则时把已有逻辑改坏。

## 面试 10 问

### 1. 你为什么做这个项目？

因为我自己找实习时发现 BOSS 上岗位很多，人工逐条看 JD、判断是否匹配、再写开场白很耗时。所以我把这个流程拆成插件抓取、后端匹配和 LLM 生成开场白三个环节，用工具减少重复劳动。

### 2. 整体架构是什么？

整体是 Chrome 插件 + FastAPI 后端 + 匹配流水线。插件负责读取 BOSS 页面岗位信息并展示结果；FastAPI 提供 `/health`、`/match`、`/resume/parse`；`pipeline.py` 负责简历画像、本地快筛、LLM 开场白和兜底逻辑。

### 3. 匹配分怎么算？

核心是把 JD 要求和简历技能画像做匹配，统计命中技能、缺失技能和风险项，再计算匹配分。当前主流程以本地规则为主，LLM 不负责每条岗位的最终评分，避免成本和延迟失控。

### 4. 为什么不是每条岗位都调用 LLM？

因为批量岗位分析里，每条都调用 LLM 会慢、贵，而且失败会卡住流程。所以我设计成本地快筛优先，只有分数达到阈值的高潜岗位才调用 LLM 生成开场白；智能模式忙或超时时会回退本地结果。

### 5. FastAPI 接口怎么设计？

`/match` 接收 `jd_text`、`resume_text` 和 `mode`，Pydantic 先做输入校验。后端返回统一结构：`success/data/message/request_id`，其中 `data` 里是匹配分、命中技能、缺失技能、风险、建议、面试问题和开场白。

### 6. 出错怎么处理？

输入校验错误返回 422；鉴权失败返回 401；限流返回 429；业务异常返回 400 或 500。后端有全局异常处理，返回给用户的信息保持简洁，同时日志和 Trace 里记录 request_id、耗时、错误原因和关键状态。

### 7. 日志和 Trace 记录了什么？

日志记录请求是否成功、模式、实际引擎、本地或智能兜底、分数、风险、JD 字数、简历字数和耗时。Trace JSONL 可以记录一次匹配的输入摘要、技能摘要、命中技能、缺失技能、是否调用 LLM、LLM 返回摘要和错误原因。

### 8. 你怎么评估效果？

我先做固定 JD 回归评测集，用 `eval_accuracy.py` 验证典型高匹配、低匹配和边界岗位是否落在预期分数区间。目前本地规则 12 条样本全部通过。下一步会用 20-50 条真实 JD 做人工标注一致率评估，复盘误判原因。

### 9. 云端部署怎么做的？

后端部署在阿里云 `/opt/job-accelerator`，用 Python 虚拟环境安装依赖，systemd 保持常驻运行，Nginx 把 `/job-accelerator/` 反向代理到本机 `127.0.0.1:8000`。公网只暴露 80/443，不直接暴露 8000。

### 10. 这个项目的边界是什么？

它不是 BOSS 官方工具，也不做无人值守的全自动群发。当前快速海投会在达标岗位上自动点击「立即沟通」，再尝试选择「留在此页」继续处理下一条；使用者需要自己设置筛选条件、每日目标和投递节奏，并承担平台风控和误投风险。公开仓库不声明当前存在可用的在线后端；扩大分发前仍需在私有环境验证 HTTPS、账号系统、额度统计和隐私脱敏。

## 不要这样说

- 不要说“真实准确率 100%”，只能说“固定样本回归评测 12/12 通过”。
- 不要说“无人值守全自动海投”，应该说“按用户设定的阈值和目标自动沟通，失败时暂停提示，使用者自行承担投递节奏和账号风险”。
- 不要说“LLM 负责全部判断”，应该说“本地规则快筛为主，高潜岗位调用 LLM 生成开场白”。
- 不要公开展示真实简历、真实 HR、访问 token、API Key 或完整岗位隐私信息。
