## 1. 当前产品方向和不可违反的约束

- 产品是同一个 Chrome 插件内的两种工作模式：岗位页海投和消息页 HR 回复助手，不拆成两个互不知状态的插件。
- 用户先在 BOSS 页面设置城市、薪资、经验等筛选条件；插件负责读取 JD、匹配简历、处理达标岗位，不替代 BOSS 的筛选器。
- 海投主流程优先保证快速、可恢复；快速投递完全不依赖 LLM，智能能力失败或超时必须兜底，不能卡住海投。
- 同一个 BOSS 标签页同一时间只能执行一种页面操作。任务优先级固定为：用户手动操作 > HR 回复处理 > 海投扫描。
- 海投运行时，HR 回复助手只能发现消息、去重、加入待回复队列和提醒，不能抢页面、跳转聊天页或填输入框。
- 只有用户点击“处理回复”后，插件才可以暂停海投、定位会话、调用 `/chat/reply` 并填入草稿。
- HR 回复助手只填草稿，绝不自动发送；不自动同意附件简历，不自动交换电话或微信，不代替用户回答高风险问题。
- 不绕过 BOSS 登录、验证码、MFA、风控或反爬机制；不保存 BOSS 密码、Cookie、完整聊天记录。
- 仓库不得包含真实简历、聊天正文、API Key、朋友包访问令牌或其他隐私数据。
- 公开仓库不声明当前在线后端；朋友测试环境只允许私下注入地址和令牌，扩大分发前必须验证 HTTPS 并轮换凭据。

## 4. 已确认的事实

- BOSS 消息页刚打开时可以只有左侧会话列表，右侧详情为空；未读发现应直接读取左侧列表，不要求先打开聊天详情。
- 当前真实页面有 40 个会话卡片，其中 2 个会话带未读徽标；插件已能识别并归并为 2 个队列项。
- 同一会话可能有多条未读消息，队列数量应按会话去重，而不是按红点数字累加。
- BOSS 切换聊天会话时 URL 可能不变，不能只靠 URL 判断当前会话。
- PDF 解析、快速投递、智能投递和 HR 回复共用一个插件；朋友无需在本地运行 Python 后端。
- 后端源码包含 `/match`、`/resume/parse`、`/chat/reply` 路由，`/match` 默认走 fast，聊天接口有独立并发门控；公开仓库不证明当前私有部署状态。
- C0 历史误判发生在插件的会话证据校验层，已由插件源码修复，当时不需要修改或重新部署后端。
- 调试面板和 request ID 已能帮助区分 DOM 识别、会话定位、后端请求和安全兜底问题。

- 不要自动部署、重打朋友包或合并 `main`；这些动作仍需用户分别授权。
- 不要自动发送消息、自动同意附件简历、自动交换联系方式或绕过 BOSS 风控。
- 不要把真实聊天正文、简历、令牌、API Key 或未打码截图写入仓库。
- 不要让主窗口再次执行数小时的实现任务；主窗口只做路由、验收、记忆和交接。
